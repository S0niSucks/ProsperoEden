## Contrato contábil: unidades em bytes, MiB=2^20, GiB=2^30

| Quantidade | Significado e regra |
| --- | --- |
| Guest VA | Intervalos/endereço do CPU guest; largura/layout ainda desconhecidos. Layout de RAM guest de aproximadamente 12 GB não define sua VA. Reserva/fastmem host e suas aliases têm requisitos próprios de VA/alinhamento/contiguidade. |
| GPU VA | Apertura guest de **64 GiB = 2^36 bytes**, não 64 GiB de RAM/VRAM nem obrigação de uma reserva host contígua equivalente. Reservar, mapear e tornar residente são operações distintas. |
| Backing `B_j` | Objeto host único, com ID, geração e intervalos/offsets. Duas views do mesmo intervalo não duplicam seus dados; cobram VA, tabelas e custos reais adicionais. COW/cópia, RGBA decodificado e staging são objetos novos, não aliases. |
| Commit `C_j` | Cobrança/garantia de backing segundo o SO; no Windows pode incluir páginas não residentes garantidas por RAM/pagefile. Não é RSS nem soma de VA. A falha documentada de **20.480 MiB = 20 GiB** não prova necessidade de 20 GiB de RAM. Regras PS5 e eventual equivalente de commit são UNKNOWN; não presumir swap/overcommit. |
| Physical `P_j` | Bytes físicos efetivamente cobrados ao objeto, incluindo páginas direct/pinned mesmo fora do working set. `P_j <= B_j` com backing arredondado à granularidade real. Se o allocator nativo cobra toda a reserva, usar esse total, não fração tocada. |
| CPU/GPU `U_j,V_j,O_j` | Subconjuntos físicos residentes/acessíveis CPU e GPU, sobreposição física comprovada `O_j`. União `U_j+V_j-O_j <= P_j`; acesso pelas duas unidades não duplica GDDR6. Coerência/barreiras continuam necessárias. Mesmo conteúdo em duas alocações não autoriza subtrair overlap. |
| RSS | Working set CPU reportado; pode contar aliases/shared pages de modo específico do SO. Não cobre necessariamente buffers GPU/direct ou toda cobrança física. Reconciliar com ledger de objetos, não somar cegamente RSS + “VRAM”. |
| JIT/heaps | Código ARM→x86-64, MME JIT, metadados, heaps, stacks, frontend/áudio, tabelas, driver e caches entram no ledger. RW/RX contam uma vez somente com alias físico demonstrado e política W^X qualificada; caso contrário, contar objetos separados. |

## Orçamento parametrizado e thresholds condicionais

`B_P` = limite **real e verificado do processo**, com baseline incluída, e limites separados por classe/pool; nunca os 16 GB totais do hardware. `B_C` só existe como gate separado se sua semântica for demonstrada; “não aplicável” precisa de prova, não de um zero inventado.

Por fase/evento: `P_next = sum(P_j vivos) + H + F + X`, `C_next = sum(C_j vivos) + C_extra`. `H` cobre cobranças externas/driver não incluídas; `F` granularidade/fragmentação medida; `X` crescimento/transientes ainda não contabilizados. Não duplicar parcelas já presentes nos objetos. Objetos retired ainda aguardando fence permanecem vivos; registrar startup, JIT/shader compile, decode/upload, troca de cena e teardown, não apenas steady-state.

**Proposta de política de pesquisa, não limite PS5 conhecido:** `M=max(512 MiB, ceil(0,10*B_P), incerteza medida)`; admitir operação só se `P_next+M<=B_P`, commit aplicável também couber com margem própria, quotas por pool e maior bloco/alinhamento forem satisfeitos, e mappings/coerência estiverem provados. Sem caps/contratos: UNKNOWN/BLOCKED, nunca sucesso. A partir de 80% de `B_P-M`, parar prefetch/novos jobs e recolher somente caches reconstruíveis; retomar abaixo de 70%. Guest RAM suja não é cache descartável.

Exemplo **hipotético**, não medição: guest backing de 12 GiB com fração física `r` só se sparse/demand-backing funcionar; demais parcelas inclusive pico = 4 GiB. Para budgets hipotéticos de 8/10/12 GiB e margem de 10%, exigiria `r<=0,267/0,417/0,567`, respectivamente. Se backing guest for físico eager de 12 GiB, esses cenários falham; isso não é prova de impossibilidade de outra estratégia.

VA também tem custo: tabela densa de 64 GiB, entradas de 8 bytes, granularidade de 4 KiB ⇒ 128 MiB; 64 KiB ⇒ 8 MiB, **hipóteses ilustrativas**, não formato real. Tabelas multinível/runs exigem medição própria. Uma array RGBA8 `8192×8192×68` ocupa logicamente 17 GiB no mip-base e ~22,67 GiB na cadeia completa: inviável como eager física nesses exemplos, não como VA. Sparse/BC/recompressão só reduzem residência com backend e fidelidade provados; não descartar mips/geometry silenciosamente.

Computação: limitar workers e frames in-flight explicitamente; scratch de pico = `workers*scratch_worker + in_flight*scratch_frame`, mais pipelines sobrepostos. Medir JIT misses, custo de atomics/sincronização e caminho crítico CPU/GPU para `T=1000/F_alvo` ms. Seis cores guest não reservam seis cores host; nem todos os oito cores/16 threads do hardware estão garantidos ao processo. Largura de banda CPU+GPU+upload compete na mesma memória; capacidade aprovada não garante frame rate.

## Harness aritmético embutido — candidato para A50, NOT_RUN

Python 3.9+ padrão, sem mmap/VirtualAlloc/arrays de páginas; até 128 objetos/256 views. Copiar este único bloco para `A42/budget_model.py` apenas na execução central autorizada. Não é adaptador de core nem teste de API nativa. Backings têm IDs físicos únicos; views são `(cpu|gpu|guest, id, offset, length)`. Caps fictícios dos controles abaixo não qualificam PS5. `va_ok/pools_ok` são pré-condições externas, não provas produzidas pelo modelo.

```python
G, MIB, U64 = 1 << 30, 1 << 20, (1 << 64) - 1
def check(ok):
    if not ok:
        raise ValueError("invalid model input")
def uint(x):
    check(type(x) is int and 0 <= x <= U64)
    return x
def model(rows, views, *, bp=None, bc=None, commit="unknown", margin=MIB*512,
          cmargin=0, extra_p=0, extra_c=0, guest_va=None, host_need=0,
          host_cap=None, va_ok=False, pools_ok=False):
    # row = rounded backing bytes, commit, physical, CPU, GPU, physical overlap
    check(len(rows) <= 128 and len(views) <= 256)
    check(commit in ("unknown", "bounded", "not_applicable"))
    for n in (margin, cmargin, extra_p, extra_c, host_need): uint(n)
    for n in (bp, bc, guest_va, host_cap):
        if n is not None: uint(n)
    total = [0] * 6
    for values in rows.values():
        check(len(values) == 6)
        b, c, p, u, v, o = map(uint, values)
        check(p <= b and o <= min(u, v) and u + v - o <= p)
        total = [uint(a + z) for a, z in zip(total, values)]
    mapped = dict(cpu=0, gpu=0, guest=0)
    for space, key, off, n in views:
        check(space in mapped and key in rows)
        uint(off); uint(n)
        check(n > 0 and uint(off + n) <= rows[key][0])
        mapped[space] = uint(mapped[space] + n)
    p, c = uint(total[2] + extra_p), uint(total[1] + extra_c)
    bad = ((bp is not None and uint(p + margin) > bp) or
           (host_cap is not None and host_need > host_cap) or
           (commit == "bounded" and bc is not None and uint(c + cmargin) > bc))
    unknown = (bp is None or guest_va is None or host_cap is None or
               not va_ok or not pools_ok or commit == "unknown" or
               (commit == "bounded" and bc is None))
    status = "REJECT" if bad else "UNKNOWN" if unknown else "MODEL_FIT"
    if status == "MODEL_FIT" and 5*p >= 4*(bp-margin): status = "PRESSURE"
    return dict(status=status, backing=total[0], commit=c, physical=p,
                cpu=total[3], gpu=total[4], overlap=total[5], mapped=mapped,
                guest_va=guest_va, gpu_va=64*G, host_need=host_need)

r = {"ram": (12*G, 20*G, 4*G, 3*G, 2*G, G)}
v = [("cpu", "ram", 0, 12*G), ("gpu", "ram", 0, 12*G)]
kw = dict(bp=10*G, bc=24*G, commit="bounded", margin=G,
          guest_va=128*G, host_need=24*G, host_cap=64*G,
          va_ok=True, pools_ok=True)
a = model(r, v, **kw)
check(a["status"] == "MODEL_FIT" and a["physical"] == 4*G)
check(a["commit"] == 20*G and sum(a["mapped"].values()) == 24*G)
check(model(r, v + v, **kw)["physical"] == a["physical"])
check(model(r, v, **(kw | {"bp": 5*G}))["status"] == "PRESSURE")
check(model(r, v, **(kw | {"bp": 5*G-1}))["status"] == "REJECT")
check(model(r, v, **(kw | {"bc": 20*G-1}))["status"] == "REJECT")
check(model(r, v, **(kw | {"commit": "unknown"}))["status"] == "UNKNOWN")
check(sum((max(1,8192>>i)**2)*68*4 for i in range(14)) == 24338147920)
```

O harness valida contabilidade/limites escalares, **não** colisão/contiguidade VA, granularidade nativa, equivalência de aliases, persistência de conteúdo ou fences. `mapped` soma comprimentos de views (inclusive repetidas), não tamanho da reserva nem sua união. Telemetria real deve alimentar o ledger, incluindo metadados de views extras. Saída MODEL_FIT/PRESSURE significa apenas ajuste aritmético nas hipóteses fornecidas.
