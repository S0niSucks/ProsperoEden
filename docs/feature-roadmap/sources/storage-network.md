## P03 — SMB read-only VFS with Settings editor

### Actual source behavior

1. `S/headless/network/transport.cpp:Valid`, lines 74–90, accepts explicitly configured numeric IPv4, bounded fields, safe relative game/add-on paths, ports, timeout and cache limits. It rejects unspecified/broadcast IPv4 and credential combinations inconsistent with explicit guest access. `Session::Connect`, lines 229–255, supplies user/password/domain explicitly, selects the declared SMB2 guest versus authenticated negotiation branches, requests signing with a user and optional sealing, and contains no guest retry after failed authentication. These are app calls into the selected client, not independently verified wire behavior.
2. `S/headless/network/network.cpp:Configure/Refresh`, lines 83–147, loads saved locations and creates new sessions for discovery. It scans the configured folder and one game-folder level, omits the configured add-on subtree, and limits offered games to NSP, XCI and NRO, with at most 4096 games per location. NSZ/XCZ are deliberately excluded from network discovery to avoid implicit whole-game unpacking (`GameFile`, lines 45–51). Do not infer remote ExeFS, arbitrary recursion or all Encore direct formats.
3. `S/headless/network/transport.cpp:Session::Read`, lines 324–376, serializes access, reads 256 KiB blocks into a bounded LRU and returns the requested bytes or zero on a failure. It can have copied an earlier prefix into the caller's buffer before returning zero. `Impl::Open`, lines 185–223, retains at most 16 handles and compares size/inode/mtime metadata before and after opening. Cache identity is checked against the held entry; this is **not an immutable server snapshot or continuous content-integrity check**.
4. `S/headless/network/vfs.cpp:File`, lines 17–47, exposes shared-session-backed reads, returns false from `Resize`/`Rename`, zero from `Write`, and reports non-writability. `Container`, lines 7–16, exposes no siblings for loader probes. `Directory`, lines 48–81, exposes only NSP/XCI add-ons and one child level. Its read-only directory base is an external core dependency, not inspected here. `S/headless/network/inject.cmake`, lines 8–24, routes only `OpenMode::Read` to these adapters; other permissions return null.
5. `S/headless/network/metadata.cpp:InspectGame`, lines 22–65, uses a metadata budget, filename fallback on failure, a `.network-new` cover staging path and share-specific add-on roots. `ReadBudget` in `network.cpp`, lines 60–73, has a five-second deadline, default 32 MiB transfer budget, nested-budget charging and a 4 MiB single-allocation limit while a budget is active. `S/headless/prosperoeden/eden_services.cpp:EdenServices::games`, lines 976–1008, adds network tiles under a whole-pass 128 MiB budget. This metadata staging is not a general durable-cache transaction.
6. `S/headless/prosperoeden/eden_services.cpp:EdenServices::game_path`, lines 1011–1017, preserves a known network URI rather than joining it to a local ROM directory. `S/headless/network/identity.h:ValidGameUri`, lines 9–28, validates the credential-free `pe-net://<stable-id>/<relative-path>` history identity; `S/headless/settings_store.h:ValidGameIdentity`, line 213, admits it alongside local paths. `S/headless/main.cpp:main`, lines 665–679 and 734–743, selects network add-ons and validates known network selections separately from local files.

### Read-only, cancellation and error boundaries

- Read-only means the **remote content path** above has no app write/rename/resize route. The feature still writes local saved configuration, names, covers/history and caches. Server-side read-only permissions remain a separate safeguard.
- `S/headless/network/transport.cpp:Impl::Wait/Fail/Destroy`, lines 114–147, checks cancellation/deadline while polling in 25 ms increments, publishes fixed messages, destroys the failed session and clears its cache/handles. `Session::Cancel`, line 275, sets atomic cancellation and unhealthy flags without taking the transport mutex. Cached bytes cannot be read successfully from a poisoned session. The poll interval is **not a demonstrated end-to-end cancellation latency** for library calls, mutex waits or OS I/O.
- `S/headless/network/network.cpp:StopDiscovery/Disconnect`, lines 75–82 and 149–157, cancel/join discovery and clear offers; reconnect builds a new session rather than silently reusing a failed one. Open files retain shared session ownership (`Open`, lines 180–196); old readers remain canceled rather than following a replacement manager session. Active-game errors are read from retained sessions (`GameError/CancelGame`, lines 222–231).
- `S/headless/main.cpp:main`, lines 1691–1709 and 1946–1951, cancels network game I/O during leave-loading and checks/latches network failures after load and during runtime monitoring. `S/headless/network/guest_io.cmake`, lines 1–32, declares derived IFile/IStorage error gating intended to prevent poisoned reads being reported as guest success. Its actual selected core compatibility and full guest teardown are **unverified** under this task's core exclusion.
- Draft cancel does not write. `Editor::Enter`, lines 198–215, ignores canceled/stale keyboard answers. The UI requests cancellation while a job future exists and waits for it before returning to editing. `S/headless/network/config.cpp:WriteConfiguration`, lines 145–200, checks stop before publication, compares the expected file identity/bytes, creates private exclusive staging, syncs, rechecks and renames. **Rename is the save commit point**: cancellation afterward does not undo it; failed directory sync is a saved-with-warning result. `S/headless/network/services.cpp:EdenServices::network_save_reserved`, lines 112–119, preserves that result even if reconnect/cancellation later fails. A UI “cancel” cannot promise that a committed save was unchanged.
- `S/headless/network/services.cpp:reserve_network_job/ConfigureAndDrain/StopNetworkJobs`, lines 12–37 and 73–83, reserves before dispatch and holds admission through final discovery join. UI async creation failures report unavailable and release captured admission (`network_shares.cpp:Launcher::start_network_job`, lines 62–76). These source owners reference other source-branch services; they are not drop-in equivalents of Encore's current lifecycle.

### Credential and data safety limits

- Saved SMB passwords are plaintext JSON (`S/headless/network/config.cpp:Serialize`, lines 120–126), not encrypted credentials. The editor exposes only password state, begins replacement empty and keeps text out of UI futures (`editor.h`, lines 15–27; `editor.cpp:Text/View/Enter`, lines 54–70, 158–173 and 198–215). - The reader bounds configuration to 64 KiB, rejects links/hardlinks/non-regular files and unsafe ancestors, and its private mode can chmod the real configuration file to 0600 (`config.cpp:Parent/ReadAt`, lines 25–43 and 94–114). Parsing failures do not echo excerpts. **Reading configuration in the feature can change permissions**; no actual configuration was opened in this comparison.

Actual `AskSystemKeyboard` serializes requests, polls stop, aborts, waits for dialog termination and withholds an accepted answer if termination fails; a still-owned buffer is not reused (`S/headless/system_keyboard.cpp:AskSystemKeyboard`, lines 108–211). This can wait on another keyboard or termination; it is not instantaneous cancellation. Host implementation returns unavailable, lines 215–224.
- Prefix stat checks and read-only opens express an intent not to follow links (`transport.cpp:Impl::Stat/Open`, lines 170–223). With external library internals/server semantics excluded, they do not prove race-proof remote-root confinement, reparse handling or protection against a malicious/changing server.
- Encore's already ported release privacy policy rejects named private network/Nextendo paths before reading them (`D/tools/network_privacy.py:private_network_path/preflight_export_tree`, lines 13–18 and 40–67). That is a release-input policy, not a runtime credential store, general secret scanner or USB backup exclusion implementation.

## P04 — NFS equivalent

### Actual source behavior and difference from SMB

P04 uses the same discovery, VFS, metadata budgets, history identity, Settings workflow and session poison/reconnect behavior described for P03. It is not a separate generic filesystem mount.

- `S/headless/network/transport.cpp:Session::Connect`, lines 256–268, explicitly calls `nfs_set_version(..., 3)`, read-only mode, numeric UID/GID, disables automatic reconnect/retransmit/mount traversal/directory caching, sets block read maximum, timeout, NFS port and optional mount port, then mounts the configured export. This source supports the stated **NFS v3 branch**, not a claim for NFSv4, TLS, Kerberos or arbitrary protocol negotiation.
- `S/headless/network/transport.cpp:Valid/Impl::Path/RawStat/Open`, lines 74–90, 149–168 and 185–223, requires an absolute export, prefixes relative paths appropriately, uses lstat/type filtering and `O_RDONLY | O_NOFOLLOW` for NFS file opens, and fstats held handles. These are app declarations/calls; client/server correctness is not independently established.
- `S/headless/network/editor.cpp:Applicable/View/Change`, lines 51–53 and 158–186, hides SMB credential/encryption fields for NFS and shows UID/GID/mount-port fields. Protocol switching sets the corresponding default port and clears share plus SMB credentials in the draft. `Valid` rejects SMB credentials/encryption on NFS. UI help explicitly names numeric AUTH_SYS identity and tells the user to configure read-only access server-side (`S/headless/prosperoeden/pe/ui/network_shares.cpp:Help`, lines 34–45).

### Destination, missing adaptations and safety

The destination has neither the P03 shared pipeline nor this NFS branch/editor. General socket support does not supply an NFS export browser or VFS. The same complete app adaptations are missing; an NFS transport-only or manually edited JSON port would leave P04 incomplete.

Numeric UID/GID selection is not secure user authentication. App read-only mode is not a server permission guarantee. Do not infer confidentiality, server authenticity, privileged identity restrictions or safety against server changes. The source permits nonnegative numeric UID/GID, including zero (`transport.cpp:Valid`, lines 88–90; `editor.cpp:Assign`, lines 75–85). Whether the product should expose those values is an owner decision, not resolved here. Session cancellation remains atomic plus polled/cooperative as in P03, and failed sessions do not silently reconnect.

**Candidate files:** P03's shared existing files and **NEW, proposed** network files, particularly `headless/network/{transport.cpp,config.cpp,editor.cpp,keyboard.cpp}` and the shared VFS/discovery. The source CMake declarations name the libnfs input and disable selected optional modes (`S/headless/network/CMakeLists.txt:network_clients`, lines 9–31). No installed dependency, native API availability or transport success was checked.

**Tests needed, not executed:** explicit protocol/identity/port validation; NFS-specific field switching and credential clearing; read-only file and directory operations; link/type rejection; mount/access failures; timeout/cancel/poisoning; no auto-reconnect into changed content; one-level add-ons; URI/history and game-load error propagation; shared USB/editor/launch admission. `tools/check-network-nfs-server.py` and `headless/network/nfs_server_check.cpp` are source test candidates, not evidence of an actual NAS/PS5 trial. Native compile/link and real server read-only permission/UID/GID/export tests must be separate future evidence.

**Owner decisions still open:** accepted NFS version/security scope, numeric identity policy, fixed versus discovered mount port exposure, startup connection behavior, server-side read-only prerequisite and qualification environment. Shared P03 ownership decisions also apply. No protocol expansion or alternate architecture is chosen.

## P09 — USB bulk backup and restore

### Actual source application workflow

- `S/headless/prosperoeden/pe/ui/usb_backup.cpp:Launcher::open_usb_backup/poll_usb_backup/press_usb_backup`, lines 15–64, opens an explicit protected modal, selects backup or restore, chooses offered drives/backups, inspects before confirmation and focuses **Cancel** by default. Busy Circle requests cancellation but cannot leave the worker behind. A staged/potentially pending restore refuses all modal input and requires close/reopen. This full workflow, not just `ApplyPending`, is the source feature.
- `S/headless/prosperoeden/usb_backup_services.inc:EdenServices::begin_usb_backup`, lines 3–40, publishes admission before worker dispatch, checks filesystem/game/protected-job gates, then stops/joins named source writers before drive discovery and drains the metadata bridge. It contains specific update, Amiibo, cheat, download, sync and pairing dependencies. These owners differ from Encore's current service object; their names cannot be copied as imaginary Encore APIs.
- `usb_backup_services.inc:EdenServices::usb_backup_action`, lines 45–92, accepts only offered paths/actions and binds copy/restore confirmation to the last inspected path; restore also carries the inspected manifest digest. Inspection/copy/staging run on a worker, with status under a separate mutex. Initial thread failure releases admission; later failure leaves the session failed/not busy and closable. `cancel_usb_backup/end_usb_backup/ResumeUsbJobs`, lines 94–114, request stop, join ordinary completed/canceled work, then resume eligible jobs. A restart-locked restore cannot close this way. Source destruction stops/joins USB before collaborators are destroyed (`S/headless/prosperoeden/eden_services.cpp:EdenServices::~EdenServices`, lines 731–745).
- Service calls use exactly `Eden::kDataDir` (`usb_backup_services.inc`, lines 69–73): the tree under `/data/prosperoeden`, **not the install directory or every externally selected storage root**. Saved external absolute paths can be copied as settings while their target files remain outside the backup.
- `S/headless/usb_backup.cpp:Drives/Inspect/Backup`, lines 416–448, checks `/mnt/usb0` through `/mnt/usb7`, requires a different `st_dev` from data, computes space first, exclusively creates a new dated directory, copies, rescans source inventory, independently validates copied inventory/content and publishes `COMPLETE` last. A directory with the same data-filesystem device is not accepted as a USB target. This source check is not a physical-device attestation.
- `usb_backup.cpp:Space`, lines 201–213, reserves 32 MiB plus 16 MiB metadata and allocation overhead, using `fstatvfs` (`Available`, lines 95–100); restore estimates two payload copies. These are code requirements, not established PS5 capacities or supported primitives.

### Backup, cancellation and restore semantics

1. `S/headless/usb_backup.cpp:Parts/DirAt/Parent/Scan`, lines 40–91 and 179–199, uses descriptor-relative/no-follow opens, bounds paths/depth/entries and rejects hardlinked regular files, special nodes and nested mounts. `Hash/Copy/Validate`, lines 215–247 and 320–350, limits transfer chunks to 256 KiB, retries interrupted/short writes, checks stop between operations, hashes and independently rereads content. It does not forcibly interrupt a blocked OS call. Metadata `Read/Write`, lines 254–277, is bounded but does not inspect stop mid-call.
2. Cancel/failure during backup can leave the newly created **incomplete dated directory**; `Backup`, lines 435–447, does not roll it all back. Completed offers require parseable manifest plus matching completion digest (`Backups`, lines 450–459); full payload validation occurs at inspection/staging via `Completed`, lines 351–359. A visible offer is not yet a full content-validation result.
3. `StageRestore`, lines 467–500, revalidates against the confirmation digest, plans existing targets, checks local space, copies to a new local sibling transaction, validates again, writes plan, then exclusively publishes `pending.json`. **It does not replace active app data.** Before publication it attempts to clean its own unpublished staging. If a created pending marker cannot be durably withdrawn, `RestorePending` retains recovery data and forces the service's restart lock (`usb_backup_services.inc`, lines 78–80). After successful pending publication the worker no longer offers cancellation or ordinary launcher return.
4. `ApplyPending`, lines 502–559, is a **cold-start merge**, not an exact snapshot rollback. Unmentioned files remain; existing mentioned files move into retained `previous/`; verified staged bytes are installed with sync barriers; retries require an already-installed file to match expected content. Staging and recovery remain. After completion it writes `APPLIED` and removes the pending marker. Errors return false and retain a recoverable/mixed transaction state rather than promise automatic rollback of the whole tree.
5. `S/headless/main.cpp:main`, lines 335–350, invokes this gate after filesystem access and **before migration and app directory preparation**; false returns exit status 2. Ordinary no-pending handling avoids creating the transaction root and does not require safe-stat on that path (`ApplyPending`, lines 504–514). The source runtime ordering is evidence of intended ordering, not proof that every earlier/later code path is write-free.

### Exclusions and safety limits

- `S/headless/usb_backup.cpp:Excluded`, lines 102–129, excludes ROM/update/switch/download trees, named cache/log/shader trees, `library.json`, game extensions, the entire named secret Nextendo subtree, and exact/dot-suffixed `network-shares.json` nodes. Case and trailing dot/space handling is conservative for these protected components. `Scan`, lines 183–186, checks exclusion **before opening the child**. `Parse`, lines 299–318, and strict `Validate/Scan` reject reinjected excluded manifest/payload nodes.
- This is a **named-path policy**, not a general password/token detector. Other personal files, lawful keys/firmware under the root, and unknown configuration may be included; the backup is not encrypted. Non-dot-suffixed similarly named siblings can remain included. Release packaging privacy has a different, broader `network-shares.json*` rule in Encore and must not be conflated with backup filtering.
- Hashes detect corruption, not trusted backup authorship. Held descriptors and checks are not protection against a privileged active writer mutating app data during the transaction. External FTP writers cannot be stopped by these app gates. Source documentation explicitly states this limit (`S/docs/USB_BACKUP.md`, lines 73–77), and its integrated-host records are not console evidence (lines 276–281).
- A restore that has begun applying is not promised to leave live files unchanged on failure: some originals may already be in `previous/` and some new files installed. Fail-closed startup plus retained recovery is the actual model. Do not interpret UI “Existing data was kept” as whole-tree atomic rollback.
- Destination diagnostics deliberately avoids `statfs/statvfs` for firmware-13.60 release safety (`D/headless/prosperoeden/eden_services.cpp:EdenServices::diagnostics`, lines 2089–2110). The source backup explicitly needs **`fstatvfs`**, safe-stat, no-follow/openat and sync/rename behavior. This different API is neither proven forbidden nor proven safe by the diagnostics comment; it needs separately authorized native/filesystem evidence and a fail-closed policy. Host fixtures cannot establish its console availability or sudden-removal/power-loss durability.

### Destination boundary and actual missing adaptations

Encore currently has per-game save transfer, not a bulk backup system: `D/headless/prosperoeden/eden_services.h`, lines 61–64, and `D/headless/ryujinx_saves.h:Import/Export`, lines 213–265. `Import` renames an old save and attempts best-effort rollback after copy failure; `Export` can remove the target tree on copy failure, including pre-existing output. Neither is the USB manifest/stage/cold-start protocol. Existing `Settings::WriteFile` fixed staging is also unrelated.

Current startup performs migrations and directory preparation after the filesystem probe (`D/headless/main.cpp:main`, lines 460–482), with no USB pending-restore gate. Its writable-root probe itself can create the persistent root before that point. A future cold-start gate must be placed against **Encore's actual startup ordering**, not copied at a matching line number. `D/headless/prosperoeden/eden_services.h:EdenServices`, lines 75–87, presently has only the metadata bridge among these owners, not the source's job admission/USB worker/status/restart state. EGM explicitly says save copies/settings/caches do not share one transaction (`D/EGM.md`, lines 68–72).

Missing app work therefore includes the full UI and backend, offered-path/digest-bound confirmation, cancellation/error/restart-lock semantics, pending gate ordering, available-space/native primitive qualification, current-writer admission and drain barriers, destruction joins, privacy exclusions, and recovery/user documentation. Encore's existing Nlib/case enrichment, library snapshot/name/cover writes, preferences/history, cache cleanup, migrations and any subsequently ported writers need a real owner-by-owner coordination inventory. This report did not prove that such a complete inventory or stop/join contract already exists.

## Cross-group completion constraints

- P03/P04 share app concepts, but each needs actual transport/editor/error evidence. Declared pinned client inputs are not library availability, native link success or server qualification.
- P05 changes path routing, while P09 backs up a fixed app-data root. Their interaction cannot be resolved by treating all JSON paths as payload roots or silently relocating data.
- Network editor jobs and USB/launch/root changes need one explicitly owned admission/lifetime contract in Encore. The source implementation names real collaborators that Encore does not currently have; copying those method names is not integration.
- Current Encore local-format, ExeFS history, export/privacy, media, title/profile, graphics, input, filesystem/elevation and release boundaries must remain visible. No wholesale source CMake/frontend/core replacement is justified by this comparison.
- The unresolved decisions and excluded core/client/native behavior are limits for subsequent owners, not findings of feature safety or failure on PS5. Source origin, existing documentation passes and host fixtures do not close them.
